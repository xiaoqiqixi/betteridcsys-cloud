# 主控迁移验证运行阶段

验证运行是配置恢复与正式接管之间的独立阶段，不解除原target seal，不启动普通serve、心跳或资源执行器。
财务金额、支付、币种和历史快照不参与。此文描述完整目标；必须分别记录已实现的HTTP边界、SQL身份和宿主启动证据，不能以一个处理器代替已能启动的迁移功能。

## 当前实现边界

`control.NewVerificationConsole` 已提供独立HTTP处理器：真实身份认证、精确本地只读路由、受限状态接口、
拒绝业务写和远端观测。未接入 `serve` 或安装启动命令，不注册billing API、不创建runner/worker。
它要求调用者持有独立宿主授权，不能靠一个合法operation ID启动目标服务。普通主控启动仍受原封存限制。
HTTP入口现在还核验实际专用SQL身份，并把认证与资源查询绑定到同一个连接池。root账号准备、状态和准备阶段撤销已通过 Ubuntu22/24 同源码原生验收；宿主许可、验证运行阶段持久化和停止/接管仍未接入，不是已可启动的迁移功能。

现有账号阶段的来源证据是 `ebe7e1921087441f37aaf7386df31661a3f5d54c` 的 [18 项 CI](https://github.com/xiaoqiqixi/betteridcsys-cloud/actions/runs/40821157870)，不是下述后续功能的通过证明。新增[验证数据协议](CONTROLLER_VERIFICATION_DATA.md)独立处理认证变化与业务后像，不向普通 serve 放行，不删除原身份或封存检查。本文后半部分的逐轮记录保留当时的失败与未验项，不作为当前状态覆盖。

## 状态与权限

1. 配置发布：原会话已撤销，全库精确后像可核验，尚无目标服务。
2. root批准验证：绑定原操作、配置发布意图、原目标计划、固定Origin/监听/TLS以及有效期。批准不能来自普通Web请求，也不接受任意路径、unit或命令。
3. 受限运行：真实原账户/密码登录；仅会话、登录限流及登录/退出审计允许变化。业务、用户资料/权限/密码、资源任务、网络和历史审计前缀保持原样。
4. 停止/撤销：先拒绝新请求，再排空已有请求；不得报告已经接管或解除源隔离。
5. 正式接管：另须源持久隔离、节点单活、财务重连和有限回滚合同；不属于验证服务许可。

## HTTP 边界

使用单独的构造入口，不通过公开请求参数或普通serve开关切换。复用现有identity.Service认证、Secure/HttpOnly/SameSite Cookie、Origin/CSRF、限流和当前数据库权限。

- 明确允许：CSRF挑战、登录、当前用户、退出；已有用户/角色/身份操作回执只读；实例/任务/节点/审计、批准配置、VPC/IP/overlay及公网策略的已存在本地只读查询。
- 默认拒绝：全部其他方法/路径、所有业务写、身份变更、资源派发/核对、恢复/迁移动作，以及新加接口。GET不是自动准入理由。
- 节点metrics/observation等远端查询也拒绝；迁移候选选择和其他派发准备接口未纳入只读白名单。验证期间的节点列表不宣称节点在线；保留原心跳记录供核对，连接状态另验。
- 新的验证状态接口须真实会话，返回原操作ID、阶段和business_writes=false、node_contacts=false，不返回批准文件或秘密。
- 路径必须规范且无编码别名。各原接口仍负责查询参数、对象归属和权限校验；验证层不提升角色，也不改正常控制台协议。

## SQL 身份边界

不得用现有全表DML运行身份直接发布验证服务。`NewVerificationConsole` 从同一SQLStore构造认证服务，不再接受独立的高权限认证连接。

- 校验实际 `CURRENT_USER`、当前库、MySQL版本、partial_revokes、mandatory_roles、当前角色和完整SHOW GRANTS；任何额外、缺失、角色或转授权能力均拒绝，不自动修复。
- 专用账号仅有本库SELECT；sessions可INSERT/DELETE，login_limits可INSERT/UPDATE/DELETE。
- identity_audit只给actor/action/target/created_at四列INSERT，不给id写权限，不能回填旧审计编号。用户、业务表、原审计修改及DDL均拒绝。
- 库名中的下划线按schema GRANT通配语义转义；表级库名保持literal。仅接受本地localhost账号。策略对象不执行CREATE USER或GRANT，也不替代恢复操作所有权证明。
- 普通认证仍使用原独占行锁。受限认证先取得本库共享名称的MySQL命名互斥锁，再用FOR SHARE与普通身份写互斥，直到提交/回滚。连接无论成功还是取消均销毁，防止命名锁回到连接池后继续持有。验证连接单独设置2秒InnoDB行锁等待上限：客户端断开不保证服务器立即中断等待，不能让取消请求按默认50秒继续持锁；不重试事务，不改普通连接设置。
- 验证模式要求MySQL8.0.22+或8.4；FOR SHARE从8.0.22起只需SELECT，FOR UPDATE需要额外权限，不能为让登录跑通给身份表开放写权限。参见[MySQL锁定读文档](https://dev.mysql.com/doc/refman/8.0/en/innodb-locking-reads.html)。不改变普通安装器版本合同。

真实SQL测试要求拒绝返回1142/1143/1044权限错误，不能把网络错误或无效SQL算作成功。授权漂移涵盖全局/库/用户表/审计编号/整表INSERT/GRANT OPTION/缺失权限/未激活角色，检查不改写授权。真实HTTP并发验证旧身份revision不能穿过普通撤权锁，两个独立验证服务只能消耗最后一个匿名会话槽位。
准备与撤销必须绑定已有恢复操作和不可变意图，精确核对数据库账户/权限；不能为了加账号放宽现有恢复库存检查。

登录会修改三张认证相关表，因此验证开始后不能继续把数据库称为“逐字节等于零会话后像”。独立验证记录必须绑定开始前的完整后像，区分合法新会话/限流/追加审计与业务漂移。
宿主许可与运行租约必须与普通runtime锁隔离又互斥，保持target seal不变；有效期、撤销、重启、重复进程、端点/证书漂移均fail closed。

## 验证账号准备与状态（本地已接入，原生结果未计通过）

这一步只准备验证专用数据库账号，不安装/启动服务，不修改普通主控运行身份，不解除目标封存。

- `target-verification-plan --operation <原操作ID>` 仍是原两账号阶段的只读计划。管理员核对后，在原操作私有目录放置 `verification-approval.json`，字段精确为 `schema: 1`、`operation_id` 和本次 `plan_sha256`；文件须 root 所有、0600、单链接。入口不接收替代路径或隐式批准参数。
- `target-verification-prepare --operation <原操作ID>` 在安装锁/目标锁内重新核对完整加密源包、目标封存、恢复后像、已发布配置与批准。原两账号库存检查通过后才写不可变准备意图；任何已存在的同名账号都拒绝接管。
- MySQL 生成随机密码；固定账号绑定原操作、数据库、server UUID、原所有权回执及随机属性标记。凭据只写 root 私有文件，执行四条固定最小授权，不能从调用参数或返回 JSON 执行任意 GRANT。账户属性含义参见 [MySQL CREATE USER](https://dev.mysql.com/doc/refman/8.0/en/create-user.html) 和[账户元数据设计](https://dev.mysql.com/worklog/task/?id=13562)。
- 专用三账号检查只在原验证意图匹配后使用；原恢复入口仍保持两账号库存规则。再次检查完整授权、角色、认证插件、本地 Host 和原数据库归属；独立 Go 入口实际使用保存的密码登录，成功后才发布完成回执。
- `target-verification-status --operation <原操作ID>` 只读核验同一完整链，不补回执。重复 prepare 对已经准确完成的状态只读核对；只有完成回执丢失、账号/密码/授权/原绑定全部仍一致时，才可补回同一完成回执，不重建账号或重新授权。
- 多余或缺失授权、远程同名账号、凭据错误、批准/所有权漂移均拒绝，不撤销额外权限来隐藏漂移，不重置密码。若 CREATE 或部分 GRANT 后中断而无法确认完整状态，保留原意图和材料，不能重新 CREATE 或冒充成功；该部分状态的显式恢复/撤销仍待完成。

新增 Ubuntu22/24 原生场景使用实际安装包、MySQL、root CLI 和 Go 程序，覆盖：无批准不创建账号、外来同名账号不接管、真实登录与精确授权、super_read_only 下重复核验、丢完成回执的只读状态/明确恢复、多余授权不修复、错误密码不重置、远程同名账号拒绝，以及原配置/封存/私有材料不变。新的证明字段为原生结果必需字段，旧成功报告不能冒充这个增量已通过。

本机的参数测试和夹具合同不是 root 准备验收。新原生场景尚未运行；受限服务启动、账号撤销/排空、完整迁移浏览器、节点和财务重连、接管/回退仍未完成。

## 验证账号撤销与排空（本地增量，原生验收待执行）

固定 root 入口 `target-verification-revoke-plan`、`target-verification-revoke`、`target-verification-revoke-status` 只接受原 operation ID。沿用已确认的安装 CLI、实际 MySQL、真实客户端和保护文件测试边界，不替换身份、SQL或加密组件。

1. 只读撤销计划绑定原验证计划、原账号完成回执摘要、数据库与固定账号；无法确认准备完成的账号不能被收编为可撤销对象。该部分状态的初始 CREATE/GRANT 恢复仍单独待办。
2. 管理员批准写入原操作私有目录的 `verification-revoke-approval.json`，精确字段为 `schema: 1`、`operation_id`、`revocation_plan_sha256`。要求原所有权、完整恢复后像、正式配置及原验证批准仍匹配；不接受替代路径、force、kill、drop或unlock参数。
3. 先记录不可变撤销意图，再对准确账号执行 `ACCOUNT LOCK`。不删除账号/凭据，不修改密码/授权，不取消目标 seal，也不把锁账号当作服务排空。原 prepare/status 和 Go 凭据准备入口在撤销开始后拒绝，不能隐式重新开放。
4. 核对实际 performance_schema 连接清单：必须启用、当前观察连接可见、线程丢失计数为0；存在本账号会话或未完成认证的前台连接就不写完成回执。线程事件监测关闭不能被当作“没有连接”。不会根据易复用的连接ID强杀未知进程。
5. 已有客户端正常退出后，同一 revoke 可核验已生效的锁并补回完成回执；status只读，不补文件。已有完成回执后的账号解锁、身份/权限/凭据漂移均拒绝，不偷偷重锁或覆盖证据。重复核验可在MySQL super_read_only下执行。

[MySQL账户锁文档](https://dev.mysql.com/doc/refman/8.0/en/account-locking.html)描述新连接的账户锁；[线程清单文档](https://dev.mysql.com/doc/mysql-perfschema-excerpt/8.0/en/performance-schema-threads-table.html)区分连接行和事件监测。实际8.4.13私有库已观察到：关闭事件监测后连接仍可见；锁账号后旧连接仍能SELECT，新登录明确返回3118；只有原连接退出才计为0。该SQL探针不是Ubuntu root入口验收。

新增原生场景持有真实验证账号连接、关闭其事件监测、检查撤销不能报告成功、新登录收到完整3118、旧连接未被KILL；退出后以super_read_only验证明确恢复与只读状态，最后注入解锁漂移并验证生产入口不修复。新增证明字段是必须项，旧场景报告不能替代。

当前仍要求目标主控没有运行服务，因此这是验证账号准备阶段的可撤销闭环，不是已运行验证HTTP服务的停止/排空验收。后续宿主许可、运行期认证后像、实际源归档浏览器、节点/财务重连、单活接管与回退继续保持待办；不能因为账号已锁就标记完整迁移完成。
