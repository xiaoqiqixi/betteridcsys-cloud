# 主控迁移的节点材料连续性

本合同属于 M03，不是完整主控迁移已可用的声明。

## 必须保留的身份

现有 `NodeProfile.Digest()` 包含 CA、客户端证书和私钥的路径。迁移时直接把这些字段改成目标路径，会让已保存的节点批准摘要、任务和迁移记录失配；不能重写历史行来掩盖这个差异。

在 root 管理的主控配置中新增可选 `node_materials`：每项绑定节点 ID、原 profile SHA256，以及三个实际文件路径和各自的 SHA256。节点原有端点、地址白名单、服务端指纹和 profile 字段不变。没有该字段的配置保持原行为；这个能力不是证书轮换或修改节点身份的授权。

配置解析拒绝未知节点、重复映射、过期 profile 摘要、非法路径或摘要。实际连接前依旧核查文件所有者、权限、硬链接/符号链接、内容摘要、TLS CA、客户端密钥配对、服务端指纹及批准地址。映射已存在时不回退到旧路径；缺失、变更或权限不符都必须拒绝。进程内部的路径解析结果不能进入 JSON 或 `NodeProfile.Digest()`。

## 导出与恢复

源端导出必须读取真实生效的材料位置，并在加密索引中保留引用及摘要；不能只让连接读取新路径，而备份仍误读旧路径。离线源验证复核映射与材料摘要，支持再次迁移。新目标最终将材料放在自己管理的固定目录，不能依源包路径写入任意宿主位置；此写入与配置发布需后续目标协调器的不可变计划和封存状态批准。

材料位置连续性不代表目标有权接管节点。旧 Web 会话撤销、目标配置发布、源端退役/节点单活、地址变更和重启恢复仍由后续迁移阶段分别确认。金额、支付及财务历史快照不受影响。

## 验收界面

- 使用已约定的配置解析和真实 mTLS 连接界面，不 mock 证书加载或 TLS 握手。
- 原材料路径不存在时，已批准映射仍可完成双向认证；节点 JSON/profile 摘要保持原值。
- 文件缺失/替换、错误摘要、错误服务端指纹、同 CA 未批准客户端、符号链接/硬链接和权限漂移均失败；不尝试旧路径或重发资源请求。
- 真实源导出、离线验证、目标材料发布及再次导出需要各自回归；不能用配置单测代替这些闭环。

## 本批实现与验收范围

配置解析、实际节点连接、任务候选选择、源端隔离材料摘要、加密导出及离线源验证已经使用同一组生效位置；原 profile JSON、摘要和既有无映射配置的编码不变。真实 mTLS 回归覆盖原路径不存在的成功路径、原路径仍可用时禁止回退、三个内容摘要、文件替换/丢失/权限/链接，以及 CA、客户端身份、服务端指纹和批准地址拒绝。

本地 `go test -race ./...`、`go vet ./...`、Linux amd64 四个程序编译、实际离线验证 CLI、安装与发布合同检查通过。本地没有本轮隔离 MySQL，不据此宣称原生恢复或完整迁移通过。Ubuntu22/24 实库源主机夹具增加了“历史路径不存在、实际映射导出成功、有效 PEM 字节变化明确拒绝”的断言；须以本提交的 CI 为准。

上述首批仅增加路径连续性。目标落盘由以下独立阶段实现；会话撤销、源退役/节点接管及迁移后台不由路径连续性完成。运行时支持不是可供用户手工绕过封存的激活入口。

## 封存目标的私有材料恢复（开发中）

沿用实际加密归档 API、固定 root CLI、已安装协调器和原生实库验收边界。增加目标私有阶段，不直接创建 `/etc/aster-controller`、systemd 单元或监听服务。

1. 已安装协调器先重新验证 root 可见数据库/授权及完整导入回读；Go 入口在同一目标封存锁内再次验证导入数据，随后才允许写材料。
2. 所有输出只放在本操作的固定 `runtime` 私有目录。仅复制经过认证的 TLS、资源连接 token、节点 CA/客户端身份，以及本操作新生成的目标 DSN；绝不复制源 DSN 或按源路径写宿主文件。
3. 候选配置保留控制身份、节点 profile、资源映射、监听和已批准端点；只将材料引用映射到目标目录。保留原监听不是批准地址切换，正式发布前还需显式检查目标地址/TLS/Origin。
4. 不可变意图先 fsync；文件均独占创建并同步，最后持久化完整清单。无意图而目录已存在、意图不一致、半成品或材料漂移一律拒绝；重复调用只对照认证来源和新 DSN核验，不重写材料、不刷新口令。
5. 正常服务仍被原目标封存拒绝。材料已恢复不等于配置已发布、旧会话已撤销、源主控已退役或节点已接管。接管与回退必须使用后续阶段，不能绕过封存手工启动。

安装包协调器提供 `target-materials --operation <原ID>` 与只读的 `target-material-status --operation <原ID>`，没有目录、DSN、URL、配置覆盖或 force 参数。候选配置和材料存放在该操作的 `runtime/`，不创建运行配置入口。源 DSN 不复制；目标 DSN来自本操作此前核验过的专用数据库凭据。半成品只保留并拒绝，尚无自动补写/重置接口。

本地归档 API 回归使用实际加密包与私有文件，验证完整复制、原 profile 不变、旧 DSN 排除、只读重入以及改动/权限/链接/缺失证明/外来文件拒绝。原生场景要求 MySQL `super_read_only` 下恢复材料、再次核验、篡改拒绝与有效候选配置仍被封存；新断言必须实际通过同 SHA Ubuntu22/24 CI 后才记环境通过。

root 配置的独立有界预算扩至 256 KiB，避免加入映射后实际可用节点数低于既有 64 个；普通 HTTP/资源协议仍限 64 KiB，未放宽。配置加载、源端摘要/导出和离线再次验证使用一致预算。

## 2026-10-28 验收预算与当前证据

源版本 `1f44612` 的 [CI 40663478295](https://github.com/xiaoqiqixi/betteridcsys-cloud/actions/runs/40663478295) 最终 12/14 通过。两个原生恢复作业均明确失败 `GUEST_VM_DEADLINE_EXCEEDED`，不是恢复通过或仅跳过：Ubuntu22 在 1074 秒才进入 guest 验收，Ubuntu24 在 761 秒进入；1800 秒上限耗尽时都尚未进入数据导入。独立真实 MySQL、已有管理台浏览器及其余作业通过，不覆盖这两个失败场景。

新增材料落盘断言后的 `controller-restore` 场景固定给 3600 秒总 VM 预算，包含启动与沙箱核验；工作流给 85 分钟，容纳既有 15 分钟源 SQL 夹具、60 分钟 guest 与准备/清理。`libvirt`、单独 `controller-provision` 仍为 1800 秒，不提供任意 timeout/无限等待参数，不自动重试。加密强度、完整报告、导入/只读回读/认证拒绝/材料篡改及宿主隔离断言均保留。新同 SHA CI 必须实际走完才可记通过。

材料落盘本地实现 `1777a73` 的完整 Go race、vet、四个 Linux amd64 程序编译已通过；本机无隔离 SQL DSN，不能将此换算为真实 MySQL 或原生验收。预算调整的离线夹具合同 59 项通过；它证明固定场景策略及 CLI 拒绝任意覆盖，不证明 guest 实际完成。

后续 `ec98b4a` 的 [CI 40668985905](https://github.com/xiaoqiqixi/betteridcsys-cloud/actions/runs/40668985905) 中，MySQL22 作业 `122750654457` 在控制器测试包 10 分钟上限终止：归档检查耗时 214.05 秒、材料恢复 96.33 秒，源验证已运行 4 分 34 秒。它不是 SQL 断言失败，但整个作业仍未通过。不要据 MySQL24 或既有浏览器成功替代该门禁。

材料文件故障测试现在在一次真实认证归档作用域内顺序执行各个 chmod、链接、内容与清单故障，末尾额外重新打开加密包验证持久化重入。不重复为相同密文、同一密钥的每个文件故障执行 scrypt；归档认证/篡改测试仍各自使用实际加密输入，工作因子仍为 18，所有原断言及 10 分钟上限保留。本机两项材料测试总时间由 39.220 秒降为 13.809 秒；不能把本机耗时外推为 CI 已通过。
