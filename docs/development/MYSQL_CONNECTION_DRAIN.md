# 验证账号撤销与连接排空

`ACCOUNT LOCK` 阻止后续认证，不会终止已经建立的客户端会话。撤销完成必须同时具备：原操作和账号回执匹配、账号确实锁定、连接清单可完整观察、没有旧验证会话、没有待认证连接。不能把客户端断网、账号锁定或缺少查询结果当作排空成功。

## 区分内部线程与客户连接

MySQL 的 `performance_schema.threads.TYPE = 'FOREGROUND'` 不能单独证明它是客户连接。官方记录的 `thread/sql/compress_gtid_table` 是内部 GTID 压缩线程，但也有前台类型、进程 ID 和空用户名，见 [GTID 存储与压缩说明](https://dev.mysql.com/doc/refman/8.0/en/replication-gtids-concepts.html)。若把所有这类空用户名都算成待认证连接，真实客户全部退出后仍无法完成撤销。

生产查询只识别这一完整的已知内部形态：

- 名称严格区分大小写，等于 `thread/sql/compress_gtid_table`。
- 类型为 `FOREGROUND`，进程 ID 非空。
- 用户、主机、数据库与连接类型均为空，命令严格等于 `Daemon`。

该线程独立计数，不算客户连接；超过一个匹配实例会拒绝确认。真实验证用户名始终计入活动会话，无论其监控是否启用。其他未知、未认证或仅部分匹配的线程仍阻止完成；没有按名称前缀、所有 Daemon 或所有空用户名批量忽略的规则。

SQL 的内部形态判断使用 `COALESCE(..., FALSE)`：未知的命令或名称不能因为三值逻辑而从待认证计数中消失。查询还要求 Performance Schema 开启、当前观察者可见、线程实例无丢失。

## 回归边界

- 实库 SQL 分类合同使用生产查询和固定 CTE 行，覆盖准确内部形态、未知线程、大小写差异、空命令、不同主机/数据库/连接类型、匿名握手及真实账号。这是 SQL 语义合同，不代替宿主验收。
- Ubuntu22/24 原生场景确认实际内部线程存在，持有关闭事件监测的真实已认证连接，验证锁定不伪造排空，以及新连接确实收到 MySQL 3118。
- 另持有真实未完成握手的 Unix 连接，确认无已认证会话时仍拒绝完成。仅一次性来宾夹具暂时调整握手期限以覆盖 TCG 下的完整归档验证，随后还原；生产配置与 CI 任务期限不变。
- 客户端自行退出后，原撤销动作在 `super_read_only` 下通过精确读回确认。不发送 KILL、不删账号、不重置密码、不解锁、不重试掩盖结果。

这些检查不代表已完成源主机迁移、节点接管或真 KVM 验收；必须以相应源码的实际测试结果为准。
