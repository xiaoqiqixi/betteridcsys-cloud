# 原生 CI 的只读宿主就绪检查

## 解决的问题与不变边界

原生 Ubuntu 场景曾在启动客体前因宿主地址清单从3项变为4项而拒绝执行；新增接口无IP地址、挂在主以太接口下，路由与防火墙未变。这是已观察的证据，不是客体测试通过，也不证明新增接口一定属于某个驱动。

Azure 官方说明了合成接口与可动态绑定/撤销的 VF 接口之间的关系，见[动态绑定说明](https://learn.microsoft.com/en-us/azure/virtual-network/manage-accelerated-networking#handle-dynamic-binding-and-revocation-of-virtual-function)和[MANA Linux 接口说明](https://learn.microsoft.com/en-us/azure/virtual-network/accelerated-networking-mana-linux)。当前现象与这种初始化相符，但未采集驱动归属，不能写成已经确认的具体根因。

原来的 `HOST_NETWORK_CHANGED_BEFORE_VM` 和运行后完整地址/路由/防火墙校验保持原样。不得忽略新接口、只比较部分字段、修改基线、关闭保护或把失败重分类为成功。

## 就绪阶段

两个原生工作流在依赖准备后、调用原生 harness 之前执行：

```sh
python3 -I aster-cloud/deploy/ci/network-readiness.py
```

- 只运行原有只读地址、路由和防火墙查询；不建立虚拟机、测试夹具或网络设备，不安装软件，不改变主机配置。
- 至少观察60秒，最后至少30秒采样无变化；每5秒采样。任何字段变化都会重新计算稳定窗口，不能只过滤看起来“正常”的接口。
- 整体观察期限180秒，样本数也有固定上限；查询失败、时钟异常或持续变化均明确失败。首次慢查询耗时不算已经观察到的稳定时间。
- Linux CLI 使用独立截止计时；中断沿原查询工具的异常清理路径关闭自己创建的子进程。工作流另有4分钟外层限制。
- 输出仅含固定状态、时间、样本/变化次数与最后完整快照摘要，不输出IP、接口名、路由或防火墙明文。它明确声明没有执行原生测试，不能充当原生验收报告。
- 此后原生 harness 才建立自己的**唯一初始基线**，执行全部原检查。就绪后再次发生宿主变化仍会失败；没有重试已失败场景或重建该基线的逻辑。

这一步减少测试在宿主初始化尚未稳定时开始的概率，不承诺平台永不热插拔。任何真实运行期漂移仍保留失败证据并阻止验收。

## 验证

`test_network_readiness.py` 通过既定宿主观测和时钟边界验证：初始快照不等于就绪、迟到接口、路由/防火墙变化、持续抖动、不可读状态、时钟异常、首次慢查询以及不可绕过的固定CLI。另检查两个工作流均在原生入口前调用它，原生独立检查仍存在。

这些是明确的合成观测合同，不是真实Linux就绪证据。新增步骤需要下一次同源码原生CI执行；实际报告必须与其提交SHA对应，不能继承之前的客体成功。
