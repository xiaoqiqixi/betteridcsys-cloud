# 迁移验证进程的双运行锁

## 合同

`controllerhost.Host.PrepareVerificationRuntime` 为封存目标上的专用 root 协调进程准备运行锁。它不解除目标封存、不开放普通 `serve`，也不代表迁移或 HTTP 服务已经启动。

1. 在原 `control.lock` 排他锁内核对操作、配置和计划摘要，拒绝来源侧 fence/迁移意图，并要求原运行进程已排空。
2. 调用者在同一排他锁内执行完整授权检查。检查失败不取得运行许可；成功后再次核对目标封存未变。
3. 对同一个 `runtime.lock` 独立打开两次，并核对两份描述符确实指向同一 inode；各自取得共享锁。
4. 父进程保留无 `os.File` finalizer 的原始 CLOEXEC 描述符直至实际进程退出。`Host.Close`、GC、HTTP 关闭和后续启动失败都不释放它。
5. 返回另一独立打开的描述符，供调用者通过固定子进程的 `ExtraFiles` 显式传递；启动后父进程关闭返回文件的本地副本。

不能用 `dup` 代替第二次独立打开：Linux 的 `flock` 绑定 open-file description，复制描述符共享同一把锁，任意副本的 `LOCK_UN` 都会影响它。独立打开才能让父子分别持锁。[Linux flock(2)](https://man7.org/linux/man-pages/man2/flock.2.html)

## 调用边界

该接口只适合一次任务一个进程的 root 协调命令，不能从长驻 HTTP 服务反复调用。成功后即使未能创建子进程，也应结束协调进程，不能手工提前解锁来宣称排空。调用者仍必须完成原归档、配置、TLS、最小 SQL 身份、原数据阶段与批准期限核验，并且等明文暂存清理成功后才允许子进程接纳 HTTP。

运行锁只是本机协作式排空约束，不是分布式 fence，不抵御恶意 root，也不证明 SQL 服务端连接已经归零。完整停止必须同时确认实际子进程退出、运行锁排空和真实 MySQL 连接清单；普通目标封存始终保留。

## 原生验收

`deploy/ci/test_controller_verification_guard.py` 使用从本次源码编译的独立测试 ELF，经公共 Host API 创建真实 root 父进程和无附加组的非 root 子进程。测试 ELF 不进入正式产品二进制，不增加生产调试子命令。

- 无效操作、错误计划/配置、缺少授权及授权拒绝不得取得许可；授权过程保持排他锁。
- 重复启动被拒绝；普通运行仍受目标封存阻止。
- 检查子进程只有它自己的那份运行锁，父进程原始描述符不得跨 exec 泄漏。
- 父进程关闭 Host 对象并执行 GC 后仍未排空；子进程主动解锁也不能释放父锁。
- 父进程真实退出后，仍存活的子进程继续阻止排空；两个进程均退出后才能取得排他探测锁。
- 所有探测均要求目标封存原始字节不变；测试只清理自己的进程与随机命名目录。

夹具特意不设置父死亡信号，以独立证明“子进程暂时存活仍受锁保护”，不能把它当作生产启动器。其固定测试 UID/GID 65534 也不是生产专用服务账号设计。

目前新增实现及 Linux amd64 交叉编译已具备；Ubuntu22/24 实际执行结果须从本次源码 CI 获取。完整非 root 服务启动命令、父死亡保护、期限、systemd、原账号重新登录页面和接管/回退仍待接入，不以这项锁测试代替验收。
