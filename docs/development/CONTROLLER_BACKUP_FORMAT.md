# 主控迁移包合同（M02，实施中）

本合同面向主控搬家，不包含财务库、VM 磁盘或跨主控实例转移。不修改现有 schema、任务结果或财务引用。源端隔离通过不等于本合同已经交付。

## 密钥与容器

- 手工迁移使用每次操作独立生成的256位随机恢复密钥，不接受自选短密码。密钥只保存为 root 私有文件；不放入包内、命令参数、环境变量、日志或普通 API 响应。包和密钥通过独立安全渠道交付。
- 使用官方 `filippo.io/age` 的单一 scrypt recipient。固定工作因子18，读取方上限18，拒绝混合 recipient 和未加密文件；不自创加密流或把公钥加密误称为发送方认证。此合同是持有恢复密钥的认证，不是发行者签名，也不能抵御恢复密钥本身已泄露。
- 内层为无压缩 USTAR，只允许清单中明确列出的普通文件。拒绝路径穿越、绝对路径、符号链接/硬链接、特殊文件、重复项、未列明项、非预期模式和尾随内容。完整读取并校验 age 的最终认证后，才报告包验证成功。
- 清单绑定格式版本、主控 ID、操作 ID、源码与安装身份、schema、所有文件大小/摘要及总量。恢复时还必须匹配操作者提供的预期主控/操作 ID，不能仅相信包自述的身份。

## 数据与材料

- 只导出本版本主控迁移 SQL 定义的表；同一只读一致性事务读取所有表。保留列顺序、NULL、二进制、64位整数及微秒时间，数据以行式 JSON 的字节值编码保存，不导出可执行 SQL。
- `database/schema.json` 保存数据库字符集和默认排序规则，不继承源库名。每张表第一行保存列类型、空值约束、默认值、字符集、列/表排序规则与下一个自增值；随后每行是按列顺序排列的 base64 字节数组，SQL NULL 保持 JSON null，空字节串保持空字符串。自增值关闭当前连接的统计缓存后读取，不能用现存行最大 ID 代替已经消耗的序号。表名仅来自程序内置迁移，未知表、视图以及当前数据库账号可见的触发器、存储程序和事件均拒绝。`information_schema` 会按账号权限过滤结果；普通运行账号查询为零不能证明不存在不可见的存储对象，完整主机恢复协调器还必须验证专用库创建来源与管理权限下的对象清单。不得为此给运行账号扩大全局权限。恢复端必须与全新迁移后的目标结构比较，不能把源自述的列信息当作可执行权限。
- 原生安装器保留的 `aster_installer_ownership` 不是业务表，也不能当作任意表的排除规则。只有固定 root 私有安装回执与运行 DSN 的库名/账号、当前 MySQL UUID、精确三列结构、唯一 `id=1` 行和随机 nonce 全部匹配，才把它按来源元数据处理；没有回执、结构或内容不符仍拒绝。回执单独加密收录为 `source/database-ownership.json`，不删除源标记、不将源 nonce 作为目标库所有权。普通数据库快照入口不接受此例外。
- 包含原配置、该配置显式引用的 DSN/令牌/服务端 TLS 与节点 mTLS 材料，以及源端安装和隔离记录。引用逐一核验，不递归打包 `/etc` 或任意路径。
- `controller/materials.json` 按标签排序记录配置引用和材料摘要；材料以摘要命名去重。清单要求配置、材料索引、数据库编码信息、三份源端记录和全部 34 张表，不能少表。此结构仍在开发，未发布格式兼容承诺。
- 导出准备文件仅位于该操作拥有的 root 私有目录；不进入静态站点。加密包通过同文件系统的不可覆盖原子提交发布，失败保留操作状态且不宣布成功；临时明文按明确所有权清理。
- `export-started` 必须先持久化。之后不得通过普通本地取消解除源隔离；恢复/接管协议未完成前，导出功能不接入普通管理台。

## 导入边界

包验证不等于批准恢复。恢复必须先完成整包认证、完整性和数据验证，再在新的专用空库执行当前程序的迁移、参数化数据写入和约束检查；不执行包内 SQL，不覆盖运行库，不关闭外键验证。旧 Web 会话在目标激活前撤销；控制身份、节点证书和资源引用保留。

数据库阶段先完成全部记录格式、空值和嵌入迁移摘要检查，且只接受与操作 ID 绑定的 `aster_cloud_restore_<operation>` 空库及匹配的字符集/排序规则。之后由当前程序建立结构，再逐表比较实际列、默认值和排序规则；DDL 是真实副作用，失败后的新结构保留为未激活状态，不自动删除或复用。数据导入在事务内进行，依照实际外键依赖排序、使用参数绑定和严格模式；提交前重新读取全部行并对照认证清单逐表核对摘要。自增高水位保留，不能因末尾记录已删除而回退。

数据库阶段的空库查询不是独占所有权证明；主机恢复协调器必须持有新建库凭据、绑定本次操作并排除其他写入者，不能把任意已存在的空库当作可接管目标。

数据库恢复核心不写主机配置、不启动服务、不连接节点，也不撤销源端隔离。它的数据库往返测试不能替代软件安装身份校验、目标主机封印、会话撤销、节点控制权接管或迁移 UI。后台和安装向导必须等这些边界接齐后再开放。

## 已约定的验收边界

使用实际命令、官方 age 互操作、真实 MySQL 导出/恢复和真实主控服务验证。覆盖错误密钥、篡改、截断、尾随/重复文件、超限、非法路径、模式与身份不匹配；所有拒绝均需明确结果，不能将异常退出或网络错误计为成功。导出前后整库行快照不变；目标非空时在任何写入前拒绝。全链未通过前，能力声明保持 `migration_ready=false`。

权限可见性参考：[MySQL INFORMATION_SCHEMA](https://dev.mysql.com/doc/refman/8.4/en/information-schema-introduction.html) 与 [TRIGGERS 权限](https://dev.mysql.com/doc/refman/8.4/en/information-schema-triggers-table.html)。

参考：[age Go API](https://pkg.go.dev/filippo.io/age)；实现锁定版本、依赖扫描和互操作结果以提交记录为准。本格式尚不是已发布功能。

产品流程参考：[魔方云主控迁移教程](https://docs.idcsmart.com/docs/%E9%AD%94%E6%96%B9%E4%BA%91/8.%20%E5%85%B3%E4%BA%8E%E8%BF%81%E7%A7%BB/%E9%AD%94%E6%96%B9%E4%BA%91%E4%B8%BB%E6%8E%A7%E8%BF%81%E7%A7%BB%E6%95%99%E7%A8%8B%EF%BC%88%E6%8E%A8%E8%8D%90%EF%BC%89) 的源端备份、全新部署目标和导入恢复分步思路；不调用其 API，不照搬 SQL 文件上传执行方式。

## 离线来源检查

`aster-controller migration-validate-source -archive <私有加密包> -key-file <独立私有密钥> -controller-id <预期主控ID> -operation <预期操作ID> -source-commit <独立核对的40位源码SHA> -staging-dir <当前用户拥有的0700目录>`

这个开发期命令先完成整包认证，再从私有临时文件校验原配置、安装记录、计划和隔离回执的绑定关系；不读取包内路径指向的本机文件，不连接源数据库或节点。检查完成或拒绝后清理本次明文暂存，清理失败不报告成功。进程被强杀后的暂存恢复尚需主机协调器接管，不能将这一入口当作无人值守恢复工具。

材料索引必须和配置的每一处引用完全对应，标签有序且唯一；相同路径只能对应同一摘要，允许同一证书按内容去重，不允许夹带未引用材料。检查运行 DSN 的本地连接及危险选项限制、三个独立令牌、TLS 证书与私钥匹配、节点 CA 可解析，以及可选源库创建回执与存档 DSN 的绑定。源材料摘要沿用 Python 导出器的 ASCII JSON 字节规则，包括中文和非 BMP 路径；不会改写参与历史节点配置摘要的路径。

输出只含控制身份、数量和明确的检查边界，不含 DSN、令牌、私钥或原文件路径。`source_bindings_verified` 和 `runtime_materials_verified` 只说明包内绑定及材料结构一致，**不是**当前域名/证书有效期、远端节点信任、实际安装文件、发行者签名、数据库行语义或目标独占所有权的证明；对应的数据库、发行来源、目标恢复与迁移能力字段保持 false。空目标恢复协调器仍需验证受信安装、封存目标、专用库创建、旧会话撤销和节点接管后才能开放服务。

### 目标库保留安装器标记

普通 `RestoreEmptyDatabase` 继续要求零对象，不会按表名忽略所有权表。原生恢复的数据阶段使用独立的 `RestoreMarkedEmptyDatabase`：目标操作库名、目标私有创建回执、运行账号与实际迁移连接账号、当前 MySQL UUID、精确 InnoDB 标记结构、字符集/排序规则和唯一 nonce 行必须一致；除此之外，目标仍不得已有任何业务表或其他可见存储对象。未知表、错误账号/UUID/nonce 或标记结构漂移在业务 DDL 前拒绝。

标记不会删除、不从源包复制、不被导入行覆盖。在数据事务开始和提交前复核，SERIALIZABLE 事务持有其读取锁，避免导入期间无声改变。失败后保留目标及原标记；重复导入已填充目标仍拒绝。

这里验证的是数据阶段的实际标记绑定，**不是**新建库来源或独占写入权限的完整证明。调用者必须是持有目标私有 journal 的主机协调器，另行核对创建过程、账号 grants、root 可见的完整对象清单和目标持久封印。不得把包内的 `source/database-ownership.json` 传作目标凭据，也不得把这个 Go 内部方法直接接成普通 HTTP 恢复接口。

## 目标主机准备与持久封存

`controller-migration.py` 的 `target-plan`、`target-seal`、`target-status` 是**目标准备接口**，不是恢复完成或切换入口。使用已安装版本内的 `templates/host-management/controller-migration.py`，仅接受 `--operation <32 位小写十六进制 ID>`，不接受路径、DSN、下载地址、任意命令或跳过验证参数。

目标必须为 Ubuntu 22/24 上仅完成软件安装、尚未批准配置/创建服务的受管主控。初始兼容策略要求目标安装与备份的 `source_commit` 完全一致；不能把另一个版本、当前 `main` 或自行修改的 manifest 当作兼容升级。已配置主控、已有控制器服务/进程、源主机自身、改变的安装文件、未清理的验证中断目录均拒绝接管，不停止或删除现有业务。

输入固定为 `/var/lib/aster-controller-restore/<operation>/`，父目录和操作目录均为 root 所有的 `0700`。管理员在独立核对来源后放入三份 root `0600` 常规文件：

- `backup.age`：源主控导出的完整加密包。
- `recovery.key`：通过独立安全通道保管的恢复密钥；不放命令行、日志或源码仓库。
- `request.json`：严格字段 `schema: 1`、`controller_id`、`operation_id`、`source_commit`、`archive_sha256`；身份及摘要须来自已核对的源导出回执，不从待导入包自动采信。

操作语义：

1. **target-plan**：验证已安装文件清单、软件状态、当前可执行文件、目标 machine-id、完整 age 认证和源配置/材料绑定。输出不含秘密的安装/源主机/目标主机/配置/密文摘要。仅产生随后删除的私有验证临时文件，不创建目标运行时状态、不操作 SQL、不连接被控。
2. **target-seal**：持有安装器锁和操作锁，写入不可覆盖的 `plan.json`，重新核对输入后，在 `/var/lib/aster-controller/<controller_id>/target-restore.json` 写入并 fsync 独立封存记录。只接受全新身份，或相同操作、配置、计划摘要的重入；不收养源隔离历史或未知文件。
3. **target-status**：重新验证固定输入、完整安装与不可变计划，读取同一封存记录；不能用“没有记录”代替成功。

封存后普通 `serve`、派发、心跳、数据库迁移、管理员初始化等命令在数据库/被控 I/O 前拒绝执行。源主机的 `migration-cancel`、`migration-fence` 和导出入口不能解除目标封存。截断、损坏、权限错误及不匹配的计划保留原始证据并拒绝继续；没有自动删除、覆盖或 `--force` 解封路径。该机制是**本机准入隔离**，不是跨主机仲裁；此阶段 `database_restored`、`target_restore_approved`、`source_isolated`、`migration_ready` 均保持 false。

目标专用库准备及带标记空库导入的宿主机编排见后文；仍需完成配置/材料安全落盘、旧会话撤销、重启恢复、节点单活接管、迁移 UI 和双主机整链验收。不得据此启动新主控或宣称可以完成主控迁移。当前根权限 CI 使用真实安装器/ELF/systemd 查询与独立加密的合成源包，明确**不是**真实源导出、SQL 导入或双主机验收；对应既有原生 MySQL 源导出检查单独保留。

目标准备的 systemd 查询需要区分“没有匹配单元”和“查询失败”。systemd [v249](https://github.com/systemd/systemd/blob/v249/src/systemctl/systemctl-list-unit-files.c) 与 [v255](https://github.com/systemd/systemd/blob/v255/src/systemctl/systemctl-list-unit-files.c) 的 `list-unit-files` 在零匹配时返回 `-ENOENT`。因此查询同时包含标准 `systemd-journald.service` 作为正向对照，仍要求命令退出 0，结果只能含该精确名称；出现控制器单元、空响应或执行失败均拒绝。不会把任意非零退出、超时或系统总线错误当作“目标为空”。已加载单元另以 `list-units --all` 检查，覆盖不活跃但仍已加载的服务。

## 固定目标专用库准备（开发期，尚不等于恢复）

已封存目标新增两个只接受 `--operation` 的 root 入口：`target-database-plan` 和 `target-provision`。只能执行本次受检安装包内的协调器；不接受任意 SQL、库名、用户、凭据、路径或脚本参数。普通安装器的数据库命名限制保持原样。

数据计划在任何 APT、账号或数据库创建前完成整包认证、34 张表全部记录格式/计数、当前 12 项嵌入迁移摘要检查。它保留源字符集与排序规则，绑定已有目标计划摘要，并将目标库固定派生为 `aster_cloud_restore_<32位操作ID>`。两个账号在 31 字符合同内派生，完整操作绑定独立持久记录；前缀碰撞必须拒绝接管。**记录格式通过不等于实际列定义或外键语义通过**；实际数据库导入仍须建立内置结构并比对，这一阶段不执行导入。

显式 `target-provision` 持有安装锁和操作锁，在目标持续封存下使用官方 Ubuntu APT 准备全新专用 MySQL，只监听 Unix socket。已有财务库、数据库服务/数据目录、第三方账号、匿名或远程 root、额外角色等均拒绝，不删除或自动收编。目标数据库按认证计划的编码创建，保留独立 nonce 标记；运行账号只有本库 DML，迁移账号只有既定本库 DDL/DML，无全局权限。创建记录、凭据和数据库计划只保存在该操作的 root 私有目录。

同一操作显式重入须匹配原始不可变计划、MySQL UUID、账号归属、最小 grants、root 可见的对象清单以及真实的运行/迁移账号连接。创建响应丢失、口令文件丢失、外来对象或未知暂存文件都保留现场并拒绝，不重置账号、不重建数据库。数据库准备成功也不写运行配置、不启动主控、不解除封印、不接管节点。

### 专用库准备验收

最初新增两个固定 `controller-provision` 场景，在独立签名的 Ubuntu22/24 TCG guest 内执行真实安装器、APT、systemd、MySQL 和实际主控 ELF。与原有 libvirt 场景共用原镜像来源验证、宿主网络前后不变校验、进程沙箱和仅官方 APT 出口；不接受任意 guest 脚本或模拟 KVM。

此场景的源身份及表记录为**合成夹具**，用于验证专用库准备，不是源主机导出或完整数据库迁移。输出明确保留 `source_fixture_synthetic=true`，`database_restored/source_host_export_verified/node_takeover_verified/migration_ready=false`；发布不得挪用该门槛为完整迁移证明。真实数据恢复核心的 MySQL 往返测试仍单独执行。root 导入与只读核验的后续合同见下节；材料落盘、会话撤销、双机重启隔离与节点单活接管仍待完成。


## 固定目标数据导入与只读结果核验

`target-restore` 与 `target-data-status` 仍只接受固定操作 ID，且必须通过完整受检安装、持续目标封印、精确数据计划和真实双方凭据验证。新增入口不是激活入口；只读状态也必须重新认证完整包，不能依据磁盘上的“成功”字段放行。

首次导入前，root 协调器检查服务器全局账号/角色、其他非系统数据库、精确最小 grants、编码和空库所有权，将审批写入 root 私有 `database/import-approval.json`，绑定目标计划及目标创建回执摘要。Go 数据入口在任何目标 DDL 前以不可覆盖写入及文件/目录 fsync 创建 `import-started.json`。只允许当前内置迁移建立结构，不能执行包提供的 SQL。

DDL 和结构比较完成后、删除任何种子行或写入源数据之前，保存 `database/structure.json`：操作、库名、MySQL UUID、目标所有权、认证归档清单及全部 35 张表（34 张业务表和独立所有权标记）的完整 `SHOW CREATE TABLE` 摘要。包含外键、索引和自增高水位；不能仅以列列表证明结构未变。证明写入失败立即停止数据事务，保留未激活 DDL，不删除、重建或自动续写。

一旦 `import-started.json` 存在，重复 `target-restore` 只执行 `target-data-status` 的核验路径，不重放 DDL/INSERT，也不重置任何口令。该路径先重新检查 root 可见的完整对象/授权，再在同一只读一致性事务锁定表元数据，核对完整结构证明、所有权和全部认证数据字节摘要。任何修改行、缺失/移除外键、缺少证明、回执变化或额外对象都拒绝；网络错误不算成功。成功才报告 `database_restored=true`，目标仍不批准激活且 `migration_ready=false`。

**中断边界**：事务提交响应丢失但数据实际完整时，可通过只读重入确认。若仅写入意图、DDL 部分完成、结构证明不完整或数据事务未提交，则保留封存现场并拒绝自动重导；目前没有自动清空/修复/换操作接管接口，不宣称完整中断恢复。后续旧会话撤销须有独立阶段和转换验证，不能为了通过核验跳过会话表。

### 原生恢复验收场景

Ubuntu22/24 的固定场景扩展为 `controller-restore`，保留原专用库准备的所有拒绝断言。先在无特权宿主临时进程运行校验固定发行摘要的 MySQL，生成真实结构和包含二进制、空值、Unicode、微秒、超有符号范围整数、删除后自增高水位及会话外键的数据快照。清理该源夹具进程后，再进入签名 Ubuntu 目标 guest，用实际安装器和 root 入口导入。

验收要求：独立 SQL 核对源值；开启 MySQL `super_read_only` 后重复恢复和查询状态仍通过；篡改数据及移除外键后必须明确拒绝且不“修复”现场。源主机身份/材料记录仍为合成，报告保留 `source_fixture_synthetic=true`，不得冒称真实源主机导出、节点切换、重启恢复或 KVM 验收。此场景代码及本地合同检查不等于对应 SHA 的 Ubuntu22/24 CI 已通过，实际结果以同 SHA CI 和留存产物为准。
